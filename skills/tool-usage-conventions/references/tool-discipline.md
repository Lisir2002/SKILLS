# 工具调用总则（Tool Discipline）

> 本文件是使用一切工具的总纪律，优先于各工具的专项约定。
> 判断一句：**把工具当工具用，不把工具调用当成"文本聊天"。**

---

## D1 直接调用工具，不写成文本

需要操作文件、运行命令、搜索、请求网络时，**直接调用对应工具**，绝不要把工具调用写成普通文本或代码块（如贴一段 `readFile(...)` 文本、把命令写在回复里让用户自己跑）。

- 陈述某个文件/结构/逻辑的事实之前 → 先 `readFile` 拿到原文；
- 需要执行操作 → 直接调工具，命令放进工具的 `command` 参数；
- 代码块只用于展示**结果/产物**，不用于"假装执行"。

## D2 并行与依赖

- **无依赖的多个调用 → 一条消息内并行发起**（提速，节省往返）；
- **有依赖的调用 → 严格按顺序逐个调用**，前一个结果决定后一个参数时，绝不并行。

## D3 输出截断处理（output_truncated）

工具结果过长时会回填 **preview**：

- 若结果含 `output_truncated=true` 与 `output_path`，**完整原始输出已存到该路径**；
- 需要更多内容时用 `readFile(path=output_path, start_line=...)` **分段读取**；
- **不要**仅因输出被截断就重复执行构建、安装、测试或抓取命令（那是浪费：命令会重跑，输出一样长）。

## D4 只读探索是眼睛

- 在陈述（或基于）项目里任何文件、目录、符号、调用关系之前，先 `list` / `search` / `readFile` 看一眼现状；
- **读到的就说读了，没读到的别编**；拿不准的标"未核实/未验证"；
- 不要靠记忆补全项目结构——项目会变，记忆会过时。

## D5 失败先修根因，不盲目重试

- 命令失败先读报错定位原因（如 BusyBox 兼容问题，见 [container-compat.md](container-compat.md)）再修；
- 同一条命令**连续失败 2 次就换方法**或向用户说明，不要反复原样重试。
